# 周报整理

把零散的周报素材汇成结构化条目，做初步分析，导出草稿。

与「生产看板」是独立项目，只共享技术选型（Node 零依赖单体 + 原生前端）。

## 快速开始

```bash
node server.js
```

浏览器打开 <http://localhost:3100>

零依赖，只用 Node 内置模块，不需要 `npm install`。

## 项目结构

```
weekly-report/
├── server.js             后端：HTTP + JSON 落盘
├── config.example.json   配置模板（凭据永远为空，进版本库）
├── config.json           本地配置（填 OA 密码，不进版本库；首次启动自动生成）
├── docs/                 接口需求文档
├── lib/l0.js             L0 规则层：切分/分类/抽数/去重（纯函数，可单独测）
├── lib/internal-api.js   内部接口客户端：拉周报 + L1 语义层
├── index.html            三栏工作台页面
└── data/weeks/           数据：一周一个 JSON 文件（不进版本库）
```

## 接入内部接口

接口需求文档：**[docs/接口文档-获取周报.md](docs/接口文档-获取周报.md)**，按公司《0. 接口文件模板》编写，可直接发给 OA 维护人。

### 配置

首次启动 `server.js` 会从 `config.example.json` 自动生成 `config.json`。**改后者**，填地址和凭据，重启生效。

> `config.json` **不进版本库**——里面要填 OA 密码。模板 `config.example.json` 里凭据永远为空。

### 鉴权

OA 用的是**请求参数鉴权**（`userCode` + `password` 拼进 query），不是 HTTP 头。这是模板里的硬性规定。

配置里凭据留空 = 不带凭据；填上就自动带，代码不用改。留空时调用会被 OA 拒绝，页面上会显示 OA 返回的原话（如「缺少必填参数：userCode / password」），而不是一句含糊的失败。

### 两个入口

| 配置项 | 用途 | 页面上的入口 |
|---|---|---|
| `reports` | 从内网拉各人提交的周报，替代手工粘贴 | 顶栏「从内网拉取」 |
| `l1` | 内网大模型：归类 + 同义条目判定 | 顶栏「语义分析」 |

没配好时按钮自动禁用，鼠标悬停会说明缺什么。

### 对接时只需要改两个函数

跟看板项目「替换 `readProduction()` 一个函数即可接入真实数据源」是同一个思路，`lib/internal-api.js` 里标了两个 **★ 替换点**：

| 函数 | 什么时候要改 |
|---|---|
| `normalizeReports()` | 周报接口的返回字段名跟接口文档不同。已按文档处理 `{code, message, data}` 信封（`code` 非 0 抛出 OA 的错误原话），并认 `userName`/`content` 等字段 |
| `callL1()` | 模型网关不是 OpenAI 兼容格式 |

其余代码（超时、降级、错误处理、上层调用、页面）一律不用动。

### 降级行为

L1 的全部意义在于**可以没有**。以下情况页面照常能用，只是分得糙一点：

| 情况 | 表现 |
|---|---|
| 内网不通 / 超时 | 提示条显示具体原因，已有条目不受影响 |
| `config.json` 写坏了 | 服务照常启动，两个按钮自动禁用 |
| 接口未配置 | 按钮禁用，悬停提示要填什么 |

### 两条不可逾越的规则

**1. 人的判断永远优先于模型。** 任何人手动改过的条目（`reviewed`），L1 一律不覆盖。这个标记由**服务端**在检测到内容字段被修改时自动打上，不依赖前端传参——前端漏传一次，模型就会把人改好的结果盖回去，而且用户毫不知情。

**2. 模型只提候选，不自动合并。** L1 判定的同义条目进入候选列表，界面上用虚线边框和「◈ 同义（模型判断）」区别于字面相似的候选，并显示模型给的理由。合不合并由人点。

## 三条设计原则

**1. 机器只建议，人来确认**

相似条目只标「候选」，并排展示让人点确认。合并后可撤销，`mergedFrom` 保留来源。
自动合并是这类工具最容易翻车的地方——误合并丢掉的信息，用户根本不知道自己丢了什么。

**2. 每条条目都能点回原文**

每条记录 `sourceId` + 原文字符区间，点「原文」高亮定位。
用户不能验证一条结构化条目是从哪句话抽出来的，就不会信任右边的任何分析结论。

**3. 原始素材永不覆盖**

导入的原文只追加、不修改。所有清洗、归类、合并都在派生出的条目层做，任何时候能推倒重来。

## 接口

| 地址 | 方法 | 说明 |
|---|---|---|
| `/api/state?week=2026-W31` | GET | 一周的全部数据 + 相似候选 + 概况 |
| `/api/sources` | POST | 导入素材，返回更新后的完整视图 |
| `/api/sources` | DELETE | 删素材（连同其派生条目） |
| `/api/items` | PATCH | 改条目字段 |
| `/api/items/merge` | POST | 合并 |
| `/api/items/unmerge` | POST | 撤销合并 |
| `/api/source?id=&week=` | GET | 取原文（回溯用） |

写操作一律返回完整视图，前端整体重渲染。几百条数据的量级下，重渲染的开销远小于维护增量更新的复杂度。

## L0 规则层说明

### 相似度算法

三个信号取最优：

| 信号 | 抓什么 |
|---|---|
| 3-gram Jaccard | 用词大体相同的重复 |
| 字集 Jaccard | 语序调换（「完成看板原型，接口跑通」↔「看板原型完成，接口跑通了」） |
| 字集包含度 | **一人写详版、一人写简版** —— 周报里最常见的重复形态 |

前两者各占一半；包含度单独算并封顶 0.82，卡在 strong 阈值（0.85）以下——包含不等于等价，这类只能进「可能重复」的折叠区。

分档：`>0.85` 强候选直接提示，`0.60~0.85` 弱候选折叠。

规则层抓不住同义不同词（「完成了看板原型」↔「把大屏页面搭起来了」），那需要 L1 语义层。

### 分类优先级

```
行内标签 > 正文关键词 > 段落标题
```

- 行内标签（`下周计划：对接数据源`）是对**这一条**的明确声明，压过一切
- 段落标题（`问题：`）只是分组——组里混进一条风险很正常，所以让位于关键词

### 词表取舍：precision 优先

「待确认」不收进阻塞词表。它太常出现在文档名里（「待确认问题清单」），一收就会把「写了 3 份文档」判成阻塞。

**这个工具里误报比漏报危险**：漏标一个阻塞只是少个提示；误标一个会带着 ⚠ 直接进草稿发给领导。

### 置信度

低于 0.6 的条目在界面上标黄，提示人工复核。人改过或确认过的条目一律置 1——置信度表达的是「机器有多确定」，人确认之后这个数就没意义了。

## 已知不准的地方

规则层就是会撞名词，以下属于预期内的误判，靠界面标黄 + 人工编辑兜底：

- 「加了断连报警，连续 2 次拉取失败会弹窗」→ 判成问题（含「失败」，实际是在描述功能）
- 「写了 3 份文档，设计方案 + 待确认问题清单」→ 判成问题（撞上文档名里的「问题」）

这类需要理解语义，是 L1 层的活。
